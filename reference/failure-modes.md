# 失败模式与来源案例

仅在迁移过程遇到相似症状时阅读；这里是方法来源，不是可复制的项目配置。Agent Hub 的权威事实仍以其当下仓库与用户裁决为准。

## 案例：同一页面的两种实施

背景：已有 demo v2 与真实 Control API，Session Workspace 要从 demo 的成功态页面源级迁移，保留正式 contracts、URL、命令与测试资产。

| 症状 | 第一次尝试 | 重做后见到的改变 |
|---|---|---|
| 页面“改过”却不像 demo | 先保留约 1,300 行旧页面壳，换五个子组件；页面级布局只改几十行 | 从签收 demo 的整页模板与样式复制成功态骨架，再逐区接正式事实 |
| 18px Run 时间线漏掉 | 写了 `toTimelineTicks` 适配函数，页面未 import/render；交互清单有该项却没作施工底账 | 原型区域清单和映射矩阵中给 tick 唯一 owner；骨架截图门核出区域与节奏 |
| 测试全绿仍是假完成 | 旧轮 145 例通过，却没做整页 demo／正式页面同态对照 | 骨架做静态占位双视口结构门；接线期测试只证明行为，收口另审视觉 |
| 接线反复改目标 | 旧轮可见偏离攒到末尾询问 | 新轮先在 demo 缺陷分支做 Inspector、筛选、头部等目标态，用户看实物确认后更新精确提交；裁决记覆盖范围 |
| 测试迁移困住页面结构 | 旧 DOM 断言会误把旧 UI 锁死 | 条件性测试分诊；保行为主张，改观察方式，纯结构断言由浏览器门接管 |
| 视觉门变成本身的阻塞 | 曾逐片采双视口图，截图通道有陈旧帧／超时，产生大量重复工作 | 用户后续裁决跳过每片盲审；方法改为骨架一次、接线行为门、收口一次，布局变了再补审 |

重做轮的 `278e8c4` 落了原型区域、正式行为、映射矩阵、测试分诊和交互清单；`b055276` 交付整页骨架与前两片。骨架成功态较早看起来接近 demo，并不意味着当时已完成正式行为。后续提交 `9549838`（Debug）、`a72f602`（筛选）、`b9c0dd4`（Inspector）、`7546f63`（Composer）、`6eed0a0`（边界态）才补齐主要接线。`a001484` 对存量测试与复演清单做收口；`31ffd58`、`71b02b8`、`8634db5` 反映之后用户改变目标，不全是无效返工。

**不得从提交数量推断完成**：被复盘时测试全绿与五条写路径已有记录，但统一截图盲审与用户最终点击签收仍是需要单独核对的状态。不同会话与提交时点可能不一致；查该项目当前票面和日志。

## 如何用这份案例判断当前风险

- 说“骨架本来就差不多”时：找成功态页面区域映射和同态截图，而不是比组件数量。
- 说“函数已写”时：查真实页面导入、渲染和点击结果；死 adapter 是未实施。
- 说“测试已经绿”时：问测试验证了请求与状态，还是验证了可见页面与点击路径。
- 说“每片都必须视觉审阅”时：先问该片是否改变页面结构；只换正式数据的切片不重复结构门。
- 说“图片出错了，先继续截图试试”时：查标签页与陈旧帧；重复同因失败就升级，不无限消耗。
- 说“目标原型变了”时：查签收 commit、用户裁决与可见差异，有没有 A/C/E 式的多份进度记录互相漂移。
